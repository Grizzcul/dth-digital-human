# 数字人项目检查与三模式规划

检查日期：2026-10-15。依据当前工作区代码、两次真实 Dify 生成请求、应用参数查询、本地接口测量和官方产品文档。仓库检查前已有未提交修改，本次没有改动已有业务代码、Dify 配置或角色素材；新增诊断脚本、本报告和脱敏测量数据。

## 1. 当前项目处于什么阶段

目前是“人物展示 + 文字对话”的数字人原型：浏览器播放预先制作的透明眨眼视频，JavaScript 负责交互，Python 转发到 Dify Cloud，LLM 在云端生成回答。LivePortrait 和 RVM 只用于离线制作素材，不在聊天请求链路里。

已经做好的基础包括：素材与模型调用分离、本地规则模式、密钥仅留后端、输入校验、视频 Range 读取、后台暂停动画、减少动画设置、视频失败静态图回退、同角色会话编号恢复。规模小、依赖少、代码容易读，适合继续迭代。

目前缺少语音输入输出、音频驱动口型、随回答变化的表情、业务模式路由、历史消息恢复与跨会话记忆。当前视觉动作与回答内容无关，回复后的变化主要是人物轮廓发光，见 [script.js:307](D:/AI/dth/script.js:307)。

## 2. 与市场产品的区别

数字人产品要分两类比较：一类用于生成成片，如课程、口播、营销视频；另一类用于实时对话，如陪伴、客服、互动讲解。你的方向更接近第二类，目前主要完成了形象展示和文字对话的接通。

| 能力 | 当前项目 | 官方产品参照 |
| --- | --- | --- |
| 形象动作 | 预制眨眼视频，运行时无形象生成推理 | LiveAvatar LITE 根据输入音频实时生成同步人物视频 |
| 语音交互 | 网页未接入；Dify STT/TTS 开关均关闭 | LiveAvatar FULL 集成 VAD、语音识别、LLM、语音合成 |
| 轮次与打断 | 一轮完成前锁定输入，无停止生成接口 | Dify 支持停止流式生成；火山引擎有打断、判停与状态接口 |
| 记忆 | 按角色保存 conversation_id，刷新不恢复消息 | Tavus 提供跨会话记忆、查看与选择性删除 |
| 业务能力 | 本地没有模式、知识源或工具路由 | 火山引擎提供知识库、函数调用、MCP 等接入能力 |
| 运行代价 | 页面展示不需要实时 GPU 推理；模型仍依赖云端 | 实时人物生成需要额外的计算或服务资源 |

以上是功能支持对比，不是同条件下的速度、成本或画质排名。没有测试这些厂商的付费服务，也没有依据宣传数字推断本项目应该达到的延迟。

可发展的差异化是：同一个人物能根据场景切换做事方式，拥有可管理的记忆，并在某个具体业务中把任务完成。继续增加更多外观素材的收益，现阶段低于解决延迟、语音和业务能力。

参照：[LiveAvatar FULL](https://docs.liveavatar.com/docs/full-mode/overview)、[LiveAvatar LITE](https://docs.liveavatar.com/docs/lite-mode/overview)、[Tavus 记忆](https://docs.tavus.io/sections/conversational-video-interface/memories)、[火山引擎实时音视频文档](https://docs.volcengine.com/docs/real_time_communication?lang=zh)。

## 3. 回复慢：实测结果

原始数据在 [audit-metrics-2026-10-15.json](D:/AI/dth/docs/audit-metrics-2026-10-15.json)。

| 测量项 | 结果 | 说明 |
| --- | ---: | --- |
| 本地聊天 HTTP/JSON 中位数 | 0.90 ms | 30 次请求，使用模拟模型回答，排除云端耗时 |
| 本地聊天 HTTP/JSON P95 | 1.10 ms | 使用最近秩法；不代表高并发容量 |
| 另一聊天请求等待时，健康检查响应 | 1.50 ms | 线程模型能够处理其他请求 |
| Dify blocking 完整回答 | 6.863 s | 独立新会话，回答正文 12 字符 |
| blocking 返回的模型 usage.latency | 5.274 s | 云端报告的字段，不能直接视为纯 GPU 计算时间 |
| Dify streaming 收到响应头 | 1.173 s | 收到响应头不等于收到回答文字 |
| streaming 首段可见回答 | 7.010 s | 过滤心跳、流程开始、节点等事件后计时 |
| streaming 回答完成 | 7.552 s | 正文 19 字符，共 6 个 message 事件 |
| streaming LLM 节点耗时 | 5.971 s | 实际执行路径为 start → llm → answer |

两种云端模式各测一次，测试使用同一简短问题、各自创建新会话，生成字数和 token 数不同；不能据此给出稳定平均值，也不能认为 streaming 比 blocking 更慢。在同一条流式请求内，首段文字只比完成早约 0.54 秒，说明这个短回答样本的主要等待发生在首段文字之前。

### 已确认的原因

1. **应用主动等待完整答案。** [server.py:69](D:/AI/dth/server.py:69) 设置 `response_mode: blocking`；[server.py:85](D:/AI/dth/server.py:85) 完整读取响应；[script.js:292](D:/AI/dth/script.js:292) 等待完整 JSON；[script.js:364](D:/AI/dth/script.js:364) 才添加回答。长回答尤其容易显得卡住。
2. **本次短问题主要时间在云端模型节点。** 本地约毫秒级，模型节点约 6 秒。换前端框架、修改 Python 循环或升级显卡，缺乏能解决这段等待的证据。
3. **首字延迟缺少持续观测。** 目前后端只打印 token 用量，没有首字时间、总时间和节点耗时记录。

### 尚不能确认的原因

- 当前具体模型、推理开关、服务排队和供应商内部耗时：服务 API 的本次可见信息不足以确认，需要检查 Dify 的 LLM 节点和供应商设置。
- 上下文增长：本次新会话 prompt_tokens 为 139，不能把这个样本归因于历史过长。长会话仍应另测。
- 网络：读取 `/info`、`/parameters` 各约 1.13 秒，包含网络和服务处理；不是纯网络 RTT。不能把模型节点之外的耗时全部算成网络。
- 检索与工具：本次实际路径没有检索或工具节点；`retriever_resource.enabled=true` 不能证明该问题执行了 RAG。其他问题是否走分支仍需查看画布。

### 提速建议，按顺序实施

1. 在 Dify 用同一批短问题比较当前模型与可用的低延迟模型；核实是否启用深度推理。普通闲聊优先短、快，复杂问题再走更强的处理路径。记录首字与总时长、正确性和费用，保留对照数据。
2. 同时打通端到端流式：Dify SSE → Python 逐事件转发并 flush → 浏览器 `ReadableStream` 增量更新同一个消息气泡。只修改 `response_mode` 无法让当前前端显示流式内容。[Dify 流式规范](https://docs.dify.ai/en/api-reference/guides/streaming)
3. 三种模式分别限制回答长度与工作流：陪伴少量自然语言、客服只在需要时检索、讲解优先复用已审核脚本。动态或个性化回答不要跨用户共用缓存。
4. 为请求记录 request_id、模式、首字时间、总时间、token 用量和错误类型，避免记录密钥和不必要的聊天正文。
5. 用固定问题集覆盖新会话和长会话，再计算 P50/P95。初步产品目标可以设为普通短问答首字 P50 ≤ 2 秒、P95 ≤ 4 秒；这是建议目标，当前尚未达到，也不保证现有供应商一定能达到。

## 5. 三种可点击切换的模式

依据本次对话，暂按“个人陪伴、企业客服、直播讲解”规划；这是功能方案，本次没有把三个模式接入业务代码或云端。

| 模式 | 应有的行为 | 第一批能力 | 后续能力 |
| --- | --- | --- | --- |
| 个人陪伴 / 私人助手 | 自然、简短，延续与你的关系和偏好 | 对话恢复、人物设定、可查看/编辑/删除的偏好记忆、语音聊天 | 工具协助、计划与提醒；根据用户授权触发具体操作 |
| 企业客服 / 知识问答 | 根据资料回答，指出依据，信息不足时说明 | 资料知识库、来源引用、澄清问题、反馈与人工转接入口 | 订单查询、工单等经授权的业务接口；真实接入前不伪装成功 |
| 直播 / 营销讲解 | 按主题连续讲解，可临时回答后继续 | 产品资料、审核脚本、播放/暂停/继续、语音播报、讲解进度 | 弹幕队列、OBS 输出、实时口型；价格与库存必须来自可信实时源 |

**页面交互：** 在主界面加入“陪伴 / 客服 / 讲解”三个明确按钮，显示选中状态与简短用途说明；切换后加载该模式上次的对话。角色与模式独立选择，同一个 Grace 可以进入三种模式。全局保留字幕、停止、语音开关和历史入口。

**会话隔离：** 当前存储键只有角色名，应扩展为应用/用户/角色/模式的组合。每种模式有独立 conversation_id；切回模式时恢复其原有会话。切换时如仍在生成，需要先结束旧请求或锁定切换，旧回答不得写入新模式。

**后端与 Dify：** 小项目先保持一个 Chatflow，增加已声明的 `mode`（companion/support/presenter）和 `character` 输入，用条件分支选择相应的提示词、检索范围与处理流程。后端只接受白名单值，不接受前端传入任意系统提示词。当前云端输入字段为空，需要先在 Dify 中新增、接线、发布，再启用前端；不能只在网页上改变按钮颜色。

**上下文原则：** 模式通常应在创建对应会话时确定，不在同一个已有会话内直接改身份。陪伴记忆、企业资料与营销资料各有边界；需要共享的用户偏好应显式决定，避免自动把私人聊天带入客服检索。未来三类业务流程独立增长后，再评估是否拆成三个 Dify 应用。

## 6. 建议实施顺序与验收

1. **先解决等待体验与首字延迟。** 模型对照测量、端到端流式、可见字幕、停止生成、请求耗时记录。验收：生成时持续显示文字，停止后能够结束上游生成，流中报错能恢复输入并保留部分内容。
2. **再实现三模式。** 按钮、配置白名单、Dify 三条分支、模式独立会话和历史恢复。验收：切换后模型行为与知识来源改变，三种模式上下文互不串入，刷新可恢复可见记录。
3. **接入语音。** 先“按住说话/点击录音 → 识别 → 回答 → 分句播报”，同时提供停止播报与字幕。分句播报应尽早开始，避免等整段回答再合成。
4. **接入口型与表达。** 再选择音频驱动的人像方案，评估实时速度、8GB 级显存适配、人物一致性、授权和部署成本。现有 LivePortrait 离线素材制作结果不能证明实时口型能力。
5. **补各模式业务能力。** 陪伴记忆管理、客服资料引用和任务处理、讲解脚本与播控。多模式入口可以先完成，每种模式仍需逐项验收，避免把未接通的功能展示成已可用。
